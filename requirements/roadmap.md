# Roadmap: Candidate Future Slices

This document lists candidate future work — not committed scope. Nothing here is scheduled; each item still needs to go through proper vertical-slice scoping (and, where it involves real product decisions, a grilling session) before it becomes an active slice, the same discipline every slice through 0005 went through.

**How this differs from the repo's other planning docs:**
- `decision-log.md` records decisions already made and grilled. This document is the opposite — things not yet decided or scoped.
- `parking-lot.md` tracks specific items that were surfaced mid-work and deliberately deferred, each with its own status lifecycle (parked/promoted/closed/superseded) and a concrete originating slice. This document is a broader, standing candidate list, not tied to a single originating moment.

Update this list as things get promoted into an actual slice (move the item out, or note it here as done and point at the slice doc) or as new candidates surface.

### Capability extensions once Corrections accumulate

- **Corpus Curator-facing Correction review view.** Slice 0005 only built the write path (a Beekeeper submitting a Correction). Nothing yet lets anyone read or triage the Corrections that accumulate.

### Corpus contribution and curation

- **End-user document suggestion.** A Beekeeper points the system at a document they think should be in the corpus. This is a genuinely new requirement, not yet in `requirements.md` — it raises a real trust question this project hasn't answered: who verifies a suggested source is authoritative before it becomes grounding truth shown to every user in that jurisdiction? Unlike a Correction (which only affects the submitter's own evaluation evidence), a bad corpus addition affects everyone's answers. Needs its own scoping/grilling pass on the trust/moderation model before any code — likely a submission-plus-review-gate shape (the Corpus Curator approves before a suggested document goes live), not a direct-to-corpus write.

### Corpus growth

- **Additional jurisdictions.** V1 covers UK and US only; FR-003 explicitly notes EU coverage is deferred and must be modelled at member-state granularity when added, not as a single "EU" jurisdiction.
- **Deeper source documents per jurisdiction.** More than one document/treatment option per jurisdiction is a prerequisite for FR-004 (trade-off comparison) and FR-006 (conflict detection) to have anything real to work with. **Partially done for FR-004**: the UK jurisdiction has three real treatment-option documents (oxalic acid, Apivar/amitraz, Apiguard/thymol); the US jurisdiction now also has three (Formic Pro, HopGuard 3, Api-Bioxal/oxalic acid), added 2026-08-05 — each with genuinely different trade-off attributes (temperature constraints, organic-certification standing, application method, honey-super compatibility), sourced from real product/manufacturer and EPA-label pages. FR-006 still has no content, since a genuine real-world disagreement between two authoritative sources wasn't found during either research pass (manufacturers/regulators don't tend to publish outright contradictions) — sourcing that remains a separate, harder research task.

### Phase 2 — The Advisor (explicitly out of scope until Phase 1 is trusted)

Per the V1 Scope Boundary decision, none of this begins until Phase 1's grounding and citation behaviour is trusted:

- **FR-009 — Proposed treatment schedule.** Given hive/apiary context and history, draft a proposed treatment schedule and present it for explicit human approval. Scoped through discussion (2026-08-04) as follows:
  - **Trigger**: beekeeper-initiated, entered via a button hook in the HiveSight app (e.g. after a high mite-count reading from a frame photo) — not system/threshold-triggered. The button hands off context (hive ID, jurisdiction, the mite count that prompted the click) via a deep link, not a tighter API coupling.
  - **System-of-record split**: HiveSight, not HiveSight Advisor, owns hive identity, inspection history, and treatment history — because all of that data is fundamentally about the hive, which HiveSight already owns. The Advisor becomes a **read**-dependent consumer of HiveSight's inspection/treatment history when reasoning about a hive, and keeps its own separate, lightweight record of *what it recommended and when* for its own traceability — it does not become the system of record for what was actually applied.
  - **Proposed shape: a LangGraph suggest → wait → resume loop.** Chosen deliberately as a genuine demonstration of agentic-AI concepts (the third pillar alongside HiveSight's predictive AI and the Advisor's grounded RAG), and specifically LangGraph because a prospect contact is known to use LangChain/LangGraph — hands-on fluency with the exact tool is worth more here than a generic "agents" demo. Graph shape: (1) **Recommend** — existing grounded RAG pipeline produces a treatment recommendation; (2) **Suggest** — write a *suggested* treatment (not a canonical applied-treatment record) into HiveSight via its API; (3) **Wait** — the graph suspends, potentially for days or weeks, until the beekeeper ticks the suggestion off as done in HiveSight's own UI; (4) **Resume/close** — triggered by that completion signal (webhook or poll), the Advisor's own recommendation trail is marked fulfilled, opening the door to a future "did it work?" follow-up (comparing pre/post-treatment inspection history). The "wait" node is the actual point of the exercise — it only demonstrates something real if backed by genuine durable execution/checkpointing, not a superficial graph that can't actually survive a multi-day suspension.
  - **External prerequisite, not buildable from this repo alone**: HiveSight needs new API surface — an endpoint to accept a suggested treatment for a hive, and the ability to record treatments (with completion) against a hive. The user is adding both to HiveSight's own roadmap in parallel.
  - **Still open**: the shared hive-identity question (both systems need to agree on what a hive *is* so the Advisor's recommendation trail can be correlated with HiveSight's inspection/treatment history) is not yet resolved.
- **FR-010 — Treatment history recording.** Superseded by the system-of-record split above — this now belongs in HiveSight, not HiveSight Advisor. Retained here only as a pointer; the actual roadmap item lives on HiveSight's side.
- **FR-011 — Optional HiveSight photo-based mite-count integration.** Widened by the FR-009 discussion above: the Advisor needs *inspection history* (a trend over time), not just a single current reading, so this is a data-source relationship, not an identity/access dependency, but a richer read than originally scoped.

### Compliance and trust

- **Real user authentication**, replacing the current dev-header approach — a prerequisite for genuine multi-user use, not just multi-user domain modelling (which already exists per FR-000). Discussed 2026-08-07, not yet scoped/grilled as a slice:
  - Prompted by HiveSight independently facing the same "Auth Boundary Decision" on its own roadmap, plus the observation that a user will plausibly work across both apps and single-click continuity between them would be genuinely useful — while the two apps stay architecturally independent (V1 Scope Boundary decision), which this must not compromise.
  - **Leaning direction**: same identity provider as HiveSight (Google OIDC, per HiveSight's own "First External Login Provider" roadmap item), but *independent sessions per app* — not true SSO. A user already signed into Google gets a near-instant "Continue as X" on whichever app they open second, without either app needing a shared cookie domain or a shared auth server.
  - Store Google's `sub` (stable per-user subject identifier) as the anchor for Advisor's own User record from day one — cheap now, avoids a painful identity-reconciliation migration if a future feature ever needs to correlate "same beekeeper" across both apps.
  - **Deliberately not pursuing** a shared cookie domain or a centralised identity broker (true SSO) — that's real new infrastructure/coupling, the same category of decision as "should Advisor call into HiveSight's API" (which got its own explicit grilling rather than being adopted for convenience). At today's actual usage (one person, both apps), the cost of one extra click per app is close to zero — building shared-session infrastructure to save it would be solving a problem that doesn't exist yet, matching the reasoning that already justified deferring the Correction review gate.
  - **Before either side writes code**: worth a short cross-project alignment note to HiveSight (mirroring the BDD/contract review pattern) — not a full design, just agreeing on provider + independent-sessions + shared-`sub`-semantics before either app commits to an identity model, since a late-discovered mismatch here would be much more painful than the API/contract mismatches already caught this way.
- **Activate the `Data Deletion Request` workflow.** Currently a dormant, modelled-but-inert entity per the Retention And Deletion Planning decision — no v1 UI, no enforcement, no scheduled purge.

### Retrieval quality

- ~~**Treatment trade-off comparison scenario failing.**~~ **Fixed, 2026-08-07** — root cause was a test-timing bug, not a product regression or threshold drift as first suspected. `treatment-trade-off-comparison.steps.ts`'s `Then` step read `.answer-citations .citation-title` via `allTextContents()`, which reads the DOM once with no wait — unlike every other step file's pattern of first awaiting `.answer-view` to become visible (an auto-retrying assertion). The step was reading citations while the request was still in flight (confirmed via the failure's captured page snapshot: the "Asking..." button was still shown, disabled). Hand-computed stub-embedding distances for the actual query against all four UK passages showed the closest match well within the partial threshold (0.67 vs. 0.8), confirming the underlying grounding/citation behaviour was correct all along — only the test's wait was missing. Fixed by adding the same `await expect(page.locator(".answer-view")).toBeVisible(...)` wait used everywhere else. Full suite green (10/10) after the fix.
- **Grounding threshold recalibration — decided, 2026-08-07: not adjusting the numbers now.** See `requirements/decision-log.md`, "Grounding Threshold Recalibration." Real Voyage-embedding measurement (11 queries, both jurisdictions, against the live corpus) confirmed the upper threshold (0.55) no longer cleanly separates off-topic from loosely-related questions — but also showed the "ambiguous" and "ungrounded" tiers don't cleanly separate in the real numbers at all, so no single new threshold value would actually fix it. Root cause is structural: one Passage per Corpus Document today means a whole document's content collapses into a single distance measurement, which is inherently coarse. **Decision: leave 0.35/0.55 as-is, revisit only once passage chunking (below) exists** — chunking is the real prerequisite, not another number.
- **Passage chunking strategy — now also the explicit prerequisite for the grounding threshold recalibration above, not just a standalone quality item.** Today, each Corpus Document is exactly one Passage (the whole document). A real corpus with longer source documents will need genuine chunking logic, which doesn't exist yet. Finer-grained passages are what would actually let distance-based grounding separate relevance tiers precisely enough for a real threshold decision to be worth making again.
- **Post-hoc claim-faithfulness checking for generated answers — a real, currently-unclosed gap, not yet evidenced.** Discussed 2026-08-07: nothing in the pipeline verifies that individual sentences in a `grounded` answer are actually supported by the text of the passage they're cited against — only that the cited passage id is real (the existing hallucinated-citation-id filter, `answer_query.py`). A technically "grounded" answer (real citation, distance comfortably under threshold) could still contain a sentence or two of Claude's own pretrained knowledge woven in alongside genuine passage content, and nothing currently detects that — this is an inherent property of LLM generation (there is no architectural separation between "tokens derived from the provided context" and "tokens derived from pretraining" within a single model), not a bug to patch. The project's actual current mitigation for this is human, not technical: the Correction mechanism (FR-007) applies with no lower trust threshold on `grounded` answers specifically because a domain-expert Beekeeper can catch a subtly-wrong claim no distance calculation or citation-id check ever could. A further technical layer exists in more rigorous RAG systems — a second pass (another LLM call, or a smaller entailment/NLI model) checking each claim in the answer against the cited passage text, flagging or stripping unsupported ones — but this hasn't been built, consistent with not adding complexity ahead of a demonstrated need. **Trigger to revisit**: if Corrections data ever shows a real pattern of `grounded` answers containing claims not actually stated in their cited sources, that's the concrete evidence to justify building this; not before.
- ~~**Handle Voyage AI's free-tier rate limits properly.**~~ **Done** — see `architecture/vertical-slice-0010-voyage-retry-with-backoff.md`. `VoyageEmbeddingProvider` retries transient errors (rate limits, timeouts, connection/service errors) up to 4 attempts with exponential backoff and jitter via `tenacity`; non-retryable errors (auth, malformed request) still fail immediately. Built at the adapter level, not as a LangGraph pattern, so it protects both the plain web query flow and the agentic `TreatmentPlanWorkflow` for free.

### Test infrastructure

- **Durably resolve the stub-vs-real embedding distance-scale mismatch.** Currently solved by giving the stub and real embedding providers separate, environment-configured threshold values (see the Grounding Thresholds Are Environment-Configurable, Not a Single Hardcoded Value decision) — a working fix, but the underlying tension (a crude bag-of-words stub can't track real semantic distance) is still there; a smarter stub or a different testing strategy could remove the need for parallel threshold configs entirely.
- **Component-level UI tests.** Every UI behaviour built so far (grounding banners, citation attribution, correction flow) is verified only through Playwright/Gherkin end-to-end tests and manual browser passes — there's no lighter-weight component-test layer (e.g. Vitest + React Testing Library) for faster, more targeted UI regression coverage.
- **Move most Gherkin coverage from browser-level to API-level, in anticipation of future non-web clients (e.g. an iPhone app).** Every scenario today drives the real web UI via Playwright. Core product behaviour (grounding, citation correctness, jurisdiction isolation, comparison, corrections) is true regardless of which client consumes the API — proving it only via the browser means a second UI would need to either re-prove the same business logic from scratch or ship with weaker coverage than the web client. The fix: prove core behaviour once via API-level Gherkin (calling `TestClient` directly, no browser), and shrink the Playwright suite to the small set of scenarios where the UI itself is genuinely the thing being verified (does this screen render the citation list, does the warning banner show). **Explicit constraint carried into this work**: moving the seam must never make the `.feature` file text more technical. The discipline already exists in this project's step-definition files — the `.feature` text stays pure business language (e.g. "the Answer's citation is flagged as superseded"), and all technical detail (a Playwright locator today, a `TestClient` call after this change) stays inside the step definition, invisible to a non-code-reading audit. If a future scenario reads like `Given a POST request is sent to /queries`, that's the tell the discipline slipped — this is the exact anti-pattern the shared `sdlc-delivery-acceptance-bdd` skill already names ("step text copied from route names or function names").
  - **Guarding against "business logic proven, but the UI isn't actually wired to it correctly."** Narrowing most scenarios to API-level doesn't mean abandoning UI-integration coverage — it means splitting the concern: keep a small number of true end-to-end "golden path" scenarios per client (proving the UI is correctly wired, not re-enumerating every business rule), and rely on `advisorApiClient.test.ts`-style mocked-fetch unit tests for fast, cheap coverage of the client's own request-building/response-parsing logic. The residual risk — contract drift, where the mocked client tests assume a JSON shape the real API no longer produces — is exactly what the retained golden-path end-to-end tests catch, since they hit the real server. If this needs to be more rigorous later, a generated/typed client from FastAPI's auto-generated OpenAPI schema would turn drift into a compile-time TypeScript error instead of something only a smoke test catches.
  - **Same Gherkin scenario, two step-definition bindings (API and UI), via a shared actor/driver abstraction.** Rather than duplicating full step-definition logic per seam (which itself risks the two implementations silently drifting apart), write each step once against an abstract actor interface (e.g. `actor.asksQuestion(jurisdiction, text)`, `actor.seesGroundedAnswer()`), with two concrete implementations — a `BrowserActor` (Playwright page interactions) and an `ApiActor` (`TestClient` calls) — selected by which config is running. This only works if feature files stay written at the level of intent, never mechanism (no "clicks the button," no "receives a 200 response") — this project's existing scenario wording is already close to that bar. Mechanically achievable with the toolchain already in place: `playwright-bdd` already supports multiple configs pointing at the same `features/*.feature` glob with different `steps` globs, exactly as `playwright.config.ts` vs `playwright.live.config.ts` already do.
